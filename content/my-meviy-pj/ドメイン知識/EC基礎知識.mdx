## ECとは

EC（Electronic Commerce / 電子商取引）= インターネット上で商品・サービスを売買する仕組み。

| 種類 | 意味 | 例 |
|------|------|-----|
| **B2C** | 企業 → 個人消費者 | Amazon、楽天 |
| **B2B** | 企業 → 企業 | meviy Marketplace、MonotaRO |
| **C2C** | 個人 → 個人 | メルカリ、ヤフオク |

meviy Marketplace は **B2B EC**（企業間取引）。

---

## ECの基本フロー

```
商品掲載 → 検索・発見 → 見積り / カート → 注文 → 決済 → 出荷 → 納品 → レビュー
```

| 要素 | 一般EC（Amazon等） | meviy Marketplace |
|------|-------------------|-------------------|
| 商品掲載 | 規格品・在庫品 | パートナーの「対応可能品目」 |
| 価格 | 固定価格 | 都度見積り（最短15分） |
| 在庫 | あり | なし（受注生産） |
| 決済 | クレカ・コンビニ払い | 請求書払い（後払い）が主流 |
| 納品 | 宅配（即日〜数日） | 工場から直送（最短1日〜） |

## 決済の仕組み

### 一般的なEC決済フロー（B2C）

```
顧客が注文
  ↓
決済代行会社（Stripe、PAY.JP等）が与信・承認
  ↓
EC事業者が売上確定
  ↓
顧客のカード / 口座から引き落とし
  ↓
EC事業者に入金
```

### meviy Marketplace（B2B）の決済フロー（推定）

B2Bでは**請求書払い（掛払い）**が業界慣習。クレカ払いはほぼ使われない。

```
バイヤーが発注・承認
  ↓
パートナーが製造・納品
  ↓
ミスミが請求書を発行（月次締め）
  ↓
バイヤーが翌月末等に銀行振込
  ↓
ミスミがパートナーへ手数料を差し引いて支払い
```

| 項目 | 内容 |
|------|------|
| **支払いサイト** | 月末締め・翌月末払いが一般的（製造業の商慣習） |
| **与信管理** | ミスミがバイヤー企業の信用審査を行う |
| **パートナーへの支払い** | GMVからテイクレートを差し引いてパートナーへ振込 |

---

## マーケットプレイスのお金の流れ

```
バイヤー（発注企業）
  ↓ 代金全額をミスミへ支払う
ミスミ（プラットフォーマー）
  ↓ テイクレート（手数料）を引いた金額をパートナーへ支払う
パートナー（加工業者）
```

**テイクレート（Take Rate）** = GMVに対するプラットフォームの取り分（%）

| プラットフォーム | テイクレート目安 |
|----------------|----------------|
| 楽天市場 | 約10〜30% |
| Amazon MP | 約8〜15% |
| meviy Marketplace | 非公開（推定10〜20%程度） |

---

## B2B決済特有の概念

| 用語 | 意味 |
|------|------|
| **掛払い** | 先に納品し、後で支払う（製造業の標準） |
| **支払いサイト** | 締め日〜支払日までの期間（例：月末締め翌月末払い） |
| **与信枠** | バイヤー企業に設定される取引限度額 |
| **GMV** | Gross Merchandise Value。プラットフォームを通じた取引の総額 |
| **NMV** | Net Merchandise Value。GMVからキャンセル・返品を除いた純取引額 |
| **テイクレート** | GMVに占めるプラットフォーム手数料の割合 |

### 主要テーブル一覧

| テーブル | 役割 |
|---------|------|
| `companies` | 企業マスタ（バイヤー・パートナー共通） |
| `users` | ユーザーアカウント（企業に所属） |
| `partner_profiles` | パートナー詳細（対応カテゴリ・審査状況） |
| `rfqs` | 見積依頼（Request for Quotation）。取引の起点 |
| `quotes` | パートナーからの見積り回答 |
| `orders` | 採用した見積りから生成される注文 |
| `invoices` | バイヤー向け月次請求書 |
| `partner_payments` | パートナーへの支払い（手数料差引後） |
| `drawing_files` | アップロードされた図面ファイル（S3等に保存） |

### データの流れ

```
1. バイヤーが図面をアップロード
   → drawing_files にレコード作成 → AI解析で parsed_metadata 更新

2. 案件（RFQ）を作成・公開
   → rfqs ステータスを open に変更 → 条件に合うパートナーへ通知

3. パートナーが見積り回答
   → quotes にレコード作成 → バイヤーへ通知

4. バイヤーが見積りを選択・発注
   → orders にレコード作成 → rfqs ステータスを ordered に変更

5. パートナーが製造・出荷・納品
   → orders ステータスを shipped → delivered に更新

6. 月次締め処理
   → invoices でバイヤーへ請求書発行
   → partner_payments でパートナーへ支払い（手数料差引）
```

### インフラ構成（推定）

| レイヤー | 技術スタック候補 | 理由 |
|---------|----------------|------|
| **DB** | PostgreSQL（RDS等） | 複雑なリレーション・JSONB対応 |
| **ファイルストレージ** | AWS S3 | 大容量図面ファイルの保存・配信 |
| **検索** | Elasticsearch | パートナー検索・フィルタリング |
| **キャッシュ** | Redis | セッション・マスタデータのキャッシュ |
| **非同期処理** | SQS + Lambda等 | 見積依頼通知・AI解析ジョブ |
| **CDN** | CloudFront等 | 図面ファイルの配信高速化 |
